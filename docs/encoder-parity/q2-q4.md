## Qualities 2-4 (H2 / H3 / H4 / H54 "quickly" hashers)

**Status: CONFIRMED.** A scratch patch to `vendor/rust-brotli/src/enc/backward_references/mod.rs`
(4 changes, ~70 lines; now part of the combined series in [patches/](patches/)) makes Rust **bit-exact with C on all 17
standard cases at q2, q3 and q4, static and flushed** (was 1/17). As a side effect it also makes
**q5-q8 17/17 exact (static and flushed)**: those were the alice29 / lcet10 / three-r128 diffs.
q0/q1 stay 17/17. q9 stays at 2/17 (different cause, not covered here).

There are no metablock, block-split, histogram or cost-model differences at q2-q4. Once the
LZ77 command streams match, the rest of the output matches too (q4 block splitting included). All
the differences are in hashing and match finding, and every one comes from a C change made after
the Rust port.

### Method

- A scratch command dumper decoded each stream with a `BROTLI_ENABLE_LOG` build of the C decoder
  and printed one line per command: `pos insert_len copy_len distance` (`MB <len>` marks each
  meta-block). Diffing C vs Rust output shows the first differing command.
  [`scripts/brstruct.py`](../../scripts/brstruct.py) gives the same view without a decoder build.
- Scratch encoders (not committed): `cenc` (C, `build/libbrotli_c.a`) and
  `renc` (a patched copy of the Rust FFI crate) share one driver, `enc.c`, which mirrors
  `streaming_harness.h` (lgwin 22, GENERIC, static = PROCESS+FINISH, flushed = 4 KiB FLUSH chunks
  + FINISH). Before patching, both reproduce the `brotli_compare --dump-dir` streams byte for byte.
  `cmp.sh "<quals>" <mode>` rebuilds `renc` and compares the 17 standard cases.

#### 1. Hash multiplier (biggest effect, q2-q4)

- **First diff:** alice29 q2, command #82 (pos 1527). C copies `" was "` (len 5) at 1538 from
  distance 669; Rust has a different bucket occupant and emits 20 literals. alice29 q3/q4 first
  differ at command #5 (pos 76: C distance 5 vs Rust distance 3 for the same 10-byte run of spaces).
- **Cause:** C commit `117b68b` ("speedup encoder on q5-9 / 1MB+ files") dropped the old
  `kHashMul64 = 0x1E35A7BD1E35A7BD` and renamed `kHashMul64Long` (`0x1FE35A7BD3579BD3`) to
  `kHashMul64`. Every user switched to the new constant, including the quickly hashers.
  - C: `c/enc/hash_base.h:21-22`; used in `c/enc/hash_longest_match_quickly_inc.h:25-30` (`HashBytes`).
  - Rust: `src/enc/backward_references/mod.rs:23` still has the old value, and
    `H2Sub/H3Sub/H4Sub/H54Sub::HashBytes` (`mod.rs:487, 535, 554, 583`) use it.
- **Evidence:** a trace of bucket key 54223 in an instrumented C copy confirmed that C and Rust map
  positions to different buckets. Switching the four `HashBytes` to `kHashMul64Long` takes q2 from
  1/17 to 15/17.
- **Fix:** use `kHashMul64Long` (i.e. C's current `kHashMul64`) in the four `HashBytes` impls.
  This makes Rust's old `kHashMul64` unused. Perf neutral. Size: q2 total over 17 cases goes
  944265 -> 944438 bytes (+0.02%, i.e. C's size).

#### 2. H2 accepts a bucket match below `kMinScore` (q2)

- **First diff (after #1):** alice29 q2 command #14438 (pos 119398) and lcet10 q2. Rust emits a
  4-byte copy from distance about 119k (`119398 1 4 119399`). C emits literals there.
- **Cause:** in the `BUCKET_SWEEP == 1` path, C only takes the bucket candidate when
  `best_score < score`. Otherwise it falls through to the static-dictionary lookup
  (`min_score == out->score`). Rust sets `out` unconditionally and returns `true`. A len-4 match at
  distance >= 2^15 scores 1920 + 4*135 - 30*15 = 2010, which is below `kMinScore` (2020), so C
  rejects it.
  - C: `c/enc/hash_longest_match_quickly_inc.h:192-216` (check at `:211`), dictionary fallback `:253`.
  - Rust: `mod.rs:421-429` (no score check).
- **Evidence:** adding the check takes q2 from 15/17 to 17/17. Removing only this check from the
  full patch takes it back to 15/17.
- **Fix:** compute the score, assign `out` and return only `if best_score < score`, else fall
  through. This removes a few long-distance len-4 copies that are below `kMinScore`. Compression
  is the same as C.

#### 3. Bucket-sweep slot layout (q3 = H3, sweep 2; q4 = H4 / H54, sweep 4)

- **First diff (after #1/#2):** q3/q4 still 1/17. Bucket contents differ from the first stores.
- **Cause:** C `#749` (2019) reorganized the quickly hasher. A key's `BUCKET_SWEEP` slots are now
  **8 apart and wrapped**: `(key + (i << 3)) & BUCKET_MASK`. The slot written is
  `(key + (ix & BUCKET_SWEEP_MASK)) & BUCKET_MASK` with `BUCKET_SWEEP_MASK = (SWEEP-1) << 3`.
  Rust still uses the pre-2019 layout: adjacent slots `key + i`, written at
  `key + ((ix >> 3) % SWEEP)`, with an over-allocated table.
  - C: `hash_longest_match_quickly_inc.h:17` (mask), `:66-72` (`Prepare`), `:103-105` (`Store`),
    `:219-224` (lookup keys and `key_out`), `:258-260` (final store).
  - Rust: `mod.rs:271` (`StoreRangeOptBasic`), `:324` (`Store`), `:343-346` (`Prepare`),
    `:431-433` (lookup loop), `:478-480` (final store).
- **Evidence:** with the C layout in all five places, q3 and q4 both go from 1/17 to 17/17.
- **Fix:** add a `sweep_slot(key, ix)` helper and use it everywhere. Also make
  `StoreRangeOptBasic` (`mod.rs:265-279`) compute the slot per position (`ix`, `ix+1`, ...;
  currently one offset for all 4) and store the **unmasked** `ix` like C (it stored `ix & mask`).
  This only matters past the ring-buffer size; a 6.5 MB test at q2-q4 is exact with the fix.
  Perf: the sweep-4 slots now span 2 cache lines instead of 1. Not measured; C accepted this.

#### 4. RLE hash-poisoning guard (q2-q9)

- **Cause:** C commit `a629289` (#590, 2017-08) narrowed the post-copy `StoreRange` when
  `sr.distance < sr.len >> 2`: `range_start = min(range_end, max(position + 2, position + sr.len - (sr.distance << 2)))`.
  Rust always stores `[position + 2, min(position + sr.len, store_end))`.
  - C: `c/enc/backward_references_inc.h:272-284`.
  - Rust: `mod.rs:2518-2523` (`CreateBackwardReferences`).
- **Evidence:** with #1-#3 applied, removing this guard drops q2/q3/q4 to 13/17 each. With it, q5,
  q6, q7 and q8 go to 17/17 static and flushed (baseline: q5 missed alice29/lcet10/three-r128, q6-8
  missed alice29/lcet10). Changes #1-#3 and #5 only touch `BasicHasher` or the end-of-block path,
  and q5-q8 here use H5/H6, so the q5-q8 improvement comes from this guard.
- **Fix:** port the 6-line guard. Small speedup on RLE data (fewer stores).
- **Note for the q5-q8 / q9 investigators:** apply this first. It fixes the q5-q8 diffs on the
  standard corpus.

#### 5. Random-heuristics jump near the end of a block (q2-q9, rare)

- **First diff:** only seen at q4 with a size hint >= 1 MiB (H54), lcet10 flushed, pos 4382 (just
  after the first 4 KiB flush). C copies len 7 from distance 310; Rust emits literals.
- **Cause:** during a literal spree, C stores every 2nd/4th position up to
  `pos_jump = min(position + 8|16, pos_end - kMargin)` and **keeps searching**. Rust, when
  `position + 16 >= pos_end - kMargin`, emits the rest of the block as literals without storing,
  and it always jumps a full 8/16.
  - C: `backward_references_inc.h:293-321`.
  - Rust: `mod.rs:2529-2546`.
- **Evidence:** with C's clamped loop (vectorized `Store4Vec4` / `StoreEvenVec4` kept when the full
  jump fits), H54 goes from 33/34 to 34/34 (17 cases × static/flushed, `SIZE_HINT=2000000`). q2-q8
  stay 17/17.
- **Fix:** as above. Perf neutral (only the tail of a block).

### Checked and found equal (not causes)

- `ChooseHasher` for q2-q4 (type = quality; H54 for q4 with size_hint >= 1 MiB): C
  `c/enc/quality.h:175-182` = Rust `src/enc/encode.rs:851-854`.
- Bucket bits / sweep / hash length / dictionary use per hasher: H2 16/1/5/yes, H3 16/2/5/no,
  H4 17/4/5/yes, H54 20/4/7/no (C `c/enc/hash.h:258-347`, Rust `mod.rs:484-586`).
- Static dictionary hash table: C `kStaticDictionaryHashWords/Lengths` and Rust
  `kStaticDictionaryHash` are identical across all 32768 entries (checked with a dump program).
  `Hash14`, `TestStaticDictionaryItem` and the `dict_num_lookups >> 7` gate match.
- Score functions (`literal_byte_score` 540 >> 2 = 135), `kMinScore`, `cost_diff_lazy = 175`,
  the lazy `sr2.len = sr.len - 1` for q < 5, and the 64-byte sparse-search window match.
- Metablock path: q2/q3 use `StoreMetaBlockTrivial`, q4 uses greedy block splitting
  (`BrotliBuildMetaBlockGreedy`). Once commands match, output is exact, so nothing differs there.
- The recent C commits `558fc64`, `cf1742a`, `42a2ed4` and `7b93874` only touch the
  experimental/SIMD hashers, Zopfli, or base64 mode (off by default). They don't affect q2-q4.

### Remaining minor differences (not seen in output, worth porting)

- C's last-distance probe also requires `cached_backward <= max_backward`
  (`hash_longest_match_quickly_inc.h:169`). Rust's `mod.rs:383` only checks `prev_ix < cur_ix`.
  This can't trigger in the tested configurations.
- The AdvHasher `StoreRangeOpt` (`mod.rs:1183`) has the same masked-`ix` store as #3 (q5-q9,
  inputs larger than the ring buffer). At q5-q8 a 6.5 MB static input still differs (C picks H6
  because `UpdateSizeHint` sets size_hint >= 1 MiB, and Rust's H6 threshold is > 4 MiB). That
  belongs to the q5-q9 hasher topic.

### Validation of the full patch

- 17 standard cases, static and flushed: q0-q8 all 17/17 exact. q9 unchanged (2/17).
- Stress inputs: alice29 with 200 KB of random bytes spliced in (exercises the random heuristics),
  and a 6.5 MB concatenation of the corpora (ring-buffer wrap). q2-q4 exact in static and flushed,
  with and without a 2 MB size hint.
- `cargo test --release --lib` on the patched crate: 43 passed, 0 failed.
